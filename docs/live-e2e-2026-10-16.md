# 真实端到端验证：DeepSeek 与 Moonshot 国内接口

验证日期：2026-10-16（Asia/Shanghai）。结果：**通过**。

使用用户授权的两个凭证，分别连接 `https://api.deepseek.com/v1` 和
`https://api.moonshot.cn/v1`。凭证通过终端隐藏输入，仅注入测试进程环境，
未保存到源码、配置、历史数据库或本报告。

## 请求与消耗

先分别调用一次 `GET /v1/models`，两次均返回 HTTP 200。账户返回的模型 ID 与
项目预设一致；为降低成本，选用 `deepseek-flash` 和 `kimi-k2.6`，关闭 thinking，
直接通过 `ModelProfile.extra_body` 将每次输出上限设为 128 tokens。
SDK 自动重试为 0，测试限制最多发送三次推理请求。

| 推理请求 | 模型 | 行为 | 输入 tokens | 输出 tokens | 结果 |
| --- | --- | --- | ---: | ---: | --- |
| 1 | deepseek-flash | 请求执行一次 `printf e2e_ok_7` | 498 | 44 | HTTP 200；finish_reason 为 tool_calls |
| 2 | kimi-k2.6 | 从旧失败快照恢复，接收 DeepSeek 的工具调用及实际工具结果 | 339 | 10 | HTTP 200；回复“通过 e2e_ok_7” |
| 3 | deepseek-flash | 接收完整历史与 Kimi 回复，继续回答 | 620 | 8 | HTTP 200；回复“通过 e2e_ok_7” |
| 合计 | | | **1,457** | **62** | **1,519 tokens** |

数字直接取自供应商返回的 usage 并相加，不是本地估算或账单金额。
DeepSeek 两次请求分别报告 256、384 个缓存命中输入 tokens；Kimi 报告 1 个
reasoning token，已包含在其输出统计中。没有追加推理请求或进行全部预设的批量测试。

## 执行路径与断言

运行实际 `chat_loop`、Apixis 图、事件工作线程、MyLLM 和官方 SDK 流式请求。
终端输入由脚本驱动；审批界面只自动批准精确匹配的 `printf e2e_ok_7`，
该命令由项目真实 shell 工具执行，退出码为 0。

1. DeepSeek 返回工具调用，Apixis 完成审批、执行和工具结果提交。
2. 在调用下一轮模型之前，注入一次本地异常，产生真实失败 context 与图快照。
   **这一步没有发送 API 请求，不是供应商真实故障。**
3. 执行 `/provider kimi kimi-k2.6`，断言原失败 context 对象仍保留，然后 `/retry`。
4. Kimi 接收旧历史及工具结果，完成同一轮回复。工具总执行次数仍为一次。
5. 执行 `/provider deepseek deepseek-flash`，在原对话中追加问题，确认上下文标记仍存在。
6. 实际 SQLite 中仅有一段对话，六条消息的角色依次为
   `user → assistant → tool → assistant → user → assistant`，没有重复用户输入。
7. 使用实际 `/history` 选择界面恢复该对话，再查看 `/transcript`。

测试过程中仅创建一个 AgentRuntime；供应商切换没有替换图或清空状态。

## 配置与验证边界

Moonshot 国内账户地址依据 [官方接入说明](https://platform.kimi.com/docs/get-api-key)。
本次在测试进程中临时将 Kimi 的 ProviderProfile.base_url 改为国内接口；
项目默认预设仍为国际地址 `https://api.moonshot.ai/v1`。国内账户使用前应将
Profile 配为 `https://api.moonshot.cn/v1`。

输出预算、thinking 开关、usage_mode 和超时也仅在本次测试的 Profile 中调整，
未改动项目的生产预设。测试通过不代表 Kimi K3、所有预设、所有推理档位、Responses
或 Anthropic/Gemini 原生签名的全部跨厂商组合均已在线验证。

临时设置和 SQLite 数据位于独立临时目录，测试结束后删除。验证记录不包含 API Key，
不依赖将付费调用加入自动单元测试。
